# Микросервис учёта кошельков цифрового рубля

Упрощённый микросервис для учёта кошельков цифрового рубля клиентов банка.

Проект сделан в рамках тестового задания и включает:
- backend на .NET 10;
- HTTP API;
- SQLite;
- простой веб-интерфейс на Vanilla JS;
- разделение проекта по принципам Clean Architecture.

## Как запустить

### Требования

- .NET 10 SDK

### Запуск

```bash
git clone <URL_ВАШЕГО_РЕПОЗИТОРИЯ>
cd wallet-service
dotnet run --project src/WalletService.WebAPI
```

После запуска приложение будет доступно по адресу, который указан в консоли, например:

```text
https://localhost:7198
```

Веб-интерфейс открывается с этого же адреса.

При старте приложение применяет миграции и, если база пустая, добавляет тестовых клиентов:

```text
MID-001
MID-002
MID-003
```

База данных хранится в SQLite (`wallet.db`).

## Основные правила

У кошелька есть четыре статуса:

| Статус | Описание |
|---|---|
| `Prcs` | Ожидает открытия |
| `Actv` | Активен |
| `Blck` | Заблокирован |
| `Clsd` | Закрыт |

Допустимые переходы:

```text
Prcs -> Actv
Actv -> Blck
Blck -> Actv
Blck -> Clsd
```

Из `Clsd` переходов нет.

Активными считаются `Prcs`, `Actv` и `Blck`. У одного клиента одновременно может быть только один такой кошелёк.

Номер счёта можно установить только один раз. Если он уже задан, заменить его нельзя.

## HTTP API

### Получение клиентов

```http
GET /api/clients
```

Пример:

```json
[
  {
    "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "mid": "MID-001",
    "fullName": "Иванов Иван Иванович",
    "participantId": "PART-101"
  }
]
```

### Получение кошельков клиента

```http
GET /api/clients/{mid}/wallets
```

Возвращает кошельки клиента по `mid`.

### Синхронизация с платформой ЦР

```http
POST /api/wallets/sync
```

Пример запроса:

```json
{
  "mid": "MID-001",
  "participantId": "PART-101",
  "walletCode": "W-10001",
  "status": "Actv",
  "accountNumber": "40817810000000000001"
}
```

Если у клиента нет активного кошелька, создаётся новый. Если активный кошелёк уже есть, данные применяются к нему.

### Изменение кошелька

```http
PATCH /api/wallets/{code}
```

Пример:

```json
{
  "status": "Blck",
  "accountNumber": null
}
```

Статус изменяется только при допустимом переходе. Номер счёта можно установить, если он ещё не задан.

## База данных

Используются две основные таблицы: `Clients` и `Wallets`.

### Clients

- `Id` — первичный ключ;
- `Mid` — уникальный идентификатор клиента;
- `FullName` — ФИО;
- `ParticipantId` — идентификатор участника на платформе ЦР, может быть `NULL`.

`Mid` уникален. `ParticipantId` также уникален, если он указан.

### Wallets

- `Id` — первичный ключ;
- `ClientId` — ссылка на клиента;
- `Code` — уникальный код кошелька;
- `AccountNumber` — номер счёта;
- `Status` — статус кошелька;
- `CreatedAt` — дата создания.

Для ограничения одного активного кошелька используется уникальный фильтрованный индекс по `ClientId`:

```sql
CREATE UNIQUE INDEX IX_Wallets_ClientId_Active
ON Wallets (ClientId)
WHERE Status IN (1, 2, 3);
```

`Clsd` не входит в это ограничение, поэтому после закрытия кошелька клиент может получить новый активный кошелёк.

## Web UI

Веб-интерфейс сделан на HTML и Vanilla JS без UI-фреймворков.

Через него можно:

- посмотреть список клиентов;
- выбрать клиента;
- посмотреть его кошельки;
- увидеть статус и номер счёта;
- отправить данные для синхронизации;
- увидеть ошибки API.

## Обработка ошибок

Ошибки предметной области обрабатываются через общий `ExceptionMiddleware`.

Для бизнес-ошибок API возвращает `400 Bad Request`:

```json
{
  "error": "текст ошибки"
}
```

Например:
- недопустимый переход статуса;
- повторная установка номера счёта;
- отсутствие клиента или кошелька;
- конфликт `ParticipantId`.

## Принятые решения

### SQLite

SQLite выбран, чтобы проект можно было запустить без PostgreSQL и других внешних сервисов.

### Автоматическая инициализация

При запуске автоматически применяются миграции. Если клиентов ещё нет, добавляются тестовые данные.

### Бизнес-правила

Основные правила находятся в доменной модели, а критичные ограничения уникальности дополнительно заданы на уровне базы данных.
